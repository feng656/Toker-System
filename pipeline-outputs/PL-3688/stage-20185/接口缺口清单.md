# 接口缺口清单

> 项目：自由光·拓客系统（一期）　责任域：产品 / 运营 / 前端与验收
> 核对方法：逐条比对 `app/api.py`（现有路由与字段）、`app/models.py`（表与字段）、`app/schemas.py`（请求体）与本阶段前端 `web/js/api/*` 的实际调用
> 版本：v1.0　编制日期：2026-11-02

本清单只登记**前端页面确实需要、但后端当前没有**的能力。前端一律以「空状态 / 占位入口 + 页面内明确提示」处理，**未改动 `app/` 任何代码**，也未臆造已实现能力。页面上的提示文案直接标注了对应的 GAP 编号。

优先级说明：**P0** 阻塞验收脚本 / 硬门槛；**P1** 影响日常运营效率；**P2** 影响体验完整性。

## 二、逐条明细

### GAP-01　统一 `/api/v1` 前缀（P1）

| 项 | 内容 |
| --- | --- |
| 接口名 | 全部 `/api/*` 路由（现前缀 `/api`） |
| 用途 | 与《分工》5.1「把 API 统一到任务书约定的 `/api/v1`」对齐，并产出 OpenAPI 3.1 |
| 期望字段 | —（路径前缀变更；响应体不变） |
| 现状 | `app/main.py`：`app.include_router(api, prefix="/api")` |
| 阻塞的页面 | 全部页面（后端一旦改前缀，前端需同步） |
| 前端处理 | 前端接口前缀集中在 `web/js/core/http.js` 的 `API_PREFIX` 一个常量，改前缀只改一处 |
| 建议 | 后端加兼容期：同时挂载 `/api` 与 `/api/v1`，前端切换后再下线旧前缀 |

### GAP-03　变体级 approve / reject + 按理由重生成 + 版本历史（P0，阻塞验收第 3、4 步）

| 项 | 内容 |
| --- | --- |
| 接口名 | `PUT /variants/{vid}/review`（approve/reject + note）、`POST /variants/{vid}/regenerate`（带 reason）、`GET /variants/{vid}/versions` |
| 用途 | 《分工》十章第 3 步「驳回 1 个版本并填写理由 → 原版本保留理由，新版本自动生成」；5.2「驳回后按原选题、平台和理由生成新变体，并保留版本历史」 |
| 期望字段 | 请求：`{action: approve\|reject, note}`；重生成请求：`{reason, keep_platform: true}`；响应：`{variant_id, version_no, parent_variant_id, body, cover_text, hashtags, quality_score, confirm_status, compliance_ok, compliance_hits, created_at}` |
| 现状 | `POST /contents/{cid}/review` 只能对**整包内容** approve/reject，理由写入 `contents.review_note`；无变体重生成、无版本历史表 |
| 阻塞的页面 | 内容管理（审核粒度、重新生成入口）、工作台（逐版本确认）、今日待办（待办条数口径） |
| 前端处理 | 内容管理页照常支持内容级通过/驳回 + 理由必填 + 顶部红条展示理由；「重新生成此版本」按钮置灰并提示「后端暂未提供变体重生成接口，见《接口缺口清单》GAP-03」 |
| 验收影响 | 《九步验收脚本与结果》第 3 步「部分通过」、第 4 步「不通过」（整包驳回导致待办剩 3 条而非 7 条） |

### GAP-08　线索 30 天去重与合并（P0，硬门槛）

| 项 | 内容 |
| --- | --- |
| 接口名 | 建议在 `POST /interactions` 的打标流程内实现；配套 `GET /leads/{id}/merged` 与 `POST /leads/{id}/merge` |
| 用途 | 《分工》十章硬门槛「同一联系方式 30 天内不能重复新建线索」；5.3「实现联系方式优先、作者和平台其次、需求相似度兜底的 30 天线索去重和合并」 |
| 期望字段 | 去重判定输入：`{contact_info, author_name, author_id, platform, need_summary, created_at}`；输出：`{is_duplicate, matched_lead_id, match_rule: contact\|author_platform\|similarity, similarity}`；合并请求：`{source_lead_id, target_lead_id, keep_notes: [...]}` |
| 现状 | `app/classifier.py` 每次打标都 `db.add(lead)`，**不做任何去重**；`Lead` 无 `repeat` 标记，也无合并记录表 |

| 验收影响 | 《九步验收脚本与结果》第 7、8 步的重复线索场景只能人工核对 |

### GAP-09　OCR 任务 + 人工确认流程（P0）

| 项 | 内容 |
| --- | --- |
| 接口名 | `POST /ocr/tasks`（或 `POST /upload/screenshot` 返回任务）、`GET /ocr/tasks?status=pending_review`、`POST /ocr/tasks/{id}/confirm`、`POST /ocr/tasks/{id}/reject` |
| 用途 | 《分工》5.3「接入截图 OCR；OCR 结果先进入 pending_review，低置信度字段强制人工确认」；十章硬门槛「OCR 低置信度不能直接入库」 |
| 期望字段 | 任务：`{id, kind: metrics\|comments, file_url, status: pending_review\|confirmed\|rejected, confidence, fields: [{name, value, confidence}], variant_id, created_at}`；确认请求：`{fields: {...}, operator}`；响应：`{task_id, status}` |
| 现状 | `POST /upload/screenshot` 只把文件存入 MinIO，返回 `{"ocr": "pending"}` 与提示「OCR 待接入，请先手工录入数据」；**无 OCR 任务表、无状态流转、无人工确认接口** |
| 阻塞的页面 | 今日待办「上传截图」、数据看板指标自动入库、线索看板评论截图识别 |
| 前端处理 | 上传后提示「截图已上传。OCR 识别尚未接入（GAP-09），请到数据看板手工录入数据」；指标只能经「数据看板 → 录入效果数据」手工录入，天然满足「低置信度不入库」 |
| 验收影响 | 《九步验收脚本与结果》第 6 步阻塞；第 7 步仅手工录入路径通过 |

### GAP-14　发布量口径与明细一致性（P0，硬门槛）

| 项 | 内容 |
| --- | --- |
| 接口名 | `GET /dashboard/funnel`（口径需明确）+ 建议新增 `GET /dashboard/reconcile` |

### GAP-16　内容变体 `blocked` 状态与变体版本历史（P0）

| 项 | 内容 |
| --- | --- |
| 接口名 | 建议 `PUT /variants/{vid}/status`（含 `blocked`）+ `GET /variants/{vid}/versions` |
| 用途 | 《分工》8.1 状态定义要求内容变体有 `draft / blocked / pending / published` 四态；十章硬门槛「红线命中不能直接放行」需要在**数据层**成立，而不只是前端不显示按钮 |
| 期望字段 | 变体：`{status: draft\|blocked\|pending\|published, block_reason, blocked_rules: [], version_no, parent_version_id}` |
| 现状 | `ContentVariant` 只有 `confirm_status(none/pending/confirmed/rejected)` 与 `publish_status(none/queued/publishing/published/failed)`；命中红线只置 `compliance_ok=false` + `compliance_hits`；**无 blocked 状态、无版本历史表** |
| 阻塞的页面 | 内容管理、今日待办、工作台（拦截只能靠前端判断，后端查询仍会返回这些变体） |
| 前端处理 | 前端对命中红线的变体：不显示「确认发布」，显示红色拦截条与命中词；保存修改后由后端重跑合规并回写 `compliance_ok` / `compliance_hits` |
| 建议 | 后端加 `status` 与 `block_reason`，并在 `GET /contents` / `GET /todo/today` 过滤或标记 blocked，前端即可改为「以后端状态为准」 |

## 四、给后端同学的一页纸

按 P0 → P1 顺序处理即可解锁一期验收：

1. **GAP-03 + GAP-16**：变体级审核 + `blocked` 状态 + 版本历史（解锁第 3、4 步，并让「红线不能放行」落到数据层）。
2. **GAP-09**：OCR 任务与人工确认（解锁第 6、7 步的截图路径）。
3. **GAP-08**：线索 30 天去重与合并（把「重复线索不新建」从人工约定变成系统约束）。
4. **GAP-14**：`publish` 接口做 URL 校验 + funnel 暴露口径字段（发布量硬门槛）。
5. 其余 P1/P2 可按迭代排期；前端对应位置已留占位与提示，后端接口就绪后前端改造量小（服务层 `web/js/api/*` 增删一行 + 页面去掉占位提示）。
